## Task 1: 修复 SimpleDateFormat 线程安全问题

**Objective:** 将 `Constant.java` 中共享的 `SimpleDateFormat` 实例改为 `ThreadLocal` 包装，确保多线程并发日志输出时不会因 `SimpleDateFormat` 非线程安全导致数据错乱。

**影响文件:**
- Modify: `orm/src/main/java/.../util/common/Constant.java` (第 25-28 行)
- No changes to SqlLog.java (调用方无需改动)

**Step 1: 修改 Constant.java**

将:
```java
  /**
   * 默认日期格式器
   */
  SimpleDateFormat DATE_FORMATTER = new SimpleDateFormat(DATE_FORMAT_STR);
```

改为:
```java
  /**
   * 默认日期格式器（ThreadLocal 确保线程安全）
   */
  ThreadLocal<SimpleDateFormat> DATE_FORMATTER = ThreadLocal.withInitial(
      () -> new SimpleDateFormat(DATE_FORMAT_STR));
```

**Step 2: 修复调用方 SqlLog.java**

SqlLog 中有两处调用 `Constant.DATE_FORMATTER.format(...)`：

第 247 行:
```java
if (param instanceof Date) return "'" + Constant.DATE_FORMATTER.format(param) + "'";
```

第 265 行:
```java
str = Constant.DATE_FORMATTER.format(value);
```

`Constant.DATE_FORMATTER` 的类型从 `SimpleDateFormat` 变为 `ThreadLocal<SimpleDateFormat>`，需改为 `.get().format(...)`:

Patch 1 (SqlLog.java:247):
```java

```

Patch 2 (SqlLog.java:265):
```java
str = Constant.DATE_FORMATTER.get().format(value);
```

## Task 2: 修复批量 INSERT 结果计数丢失

**Objective:** `BatchParameters.applyBatchParameters()` 内部中间 `executeBatch()` 结果被丢弃，导致 `OrmInserter.createInJdbcBatch()` 返回的影响行数错误。

**问题根因分析:**
- `BatchParameters.applyBatchParameters()` 当 `batchSize > 0`（默认 200）时，每 200 条执行一次 `statement.executeBatch()` 但丢弃返回值。
- `Query.executeBatch()` 随后在外部再次调用 `statement.executeBatch()`，但此时 JDBC batch 中只剩最后一批未刷新的条目（例如 250 条中的末尾 50 条），返回值 `.length = 50` 而非 `250`。
- `createInJdbcBatch()` 依赖 `.length` 判定影响行数 → 错误。

**解决方案（最小改动方案）:**

两个方案：A（改调用方）或 B（改框架层）。

**推荐方案 A** — 改动最小，1 行：在 `createInJdbcBatch()` 中使用 `entities.size()` 替代 `result.length`。

理由：每个 entity 对应 1 条 INSERT，执行成功就应计数。若 JDBC 抛出异常则程序不会到达此行。`entities.size()` 一定等于实际影响行数（非自增主键场景是按 entity 逐条插入的）。

**影响文件:**
- Modify: `orm/src/main/java/.../orm/component/OrmInserter.java` (第 259 行)

**Step 1: 修改 OrmInserter.java:259**

将:
```java
      return query.executeBatch(rs -> primaryKey.setPrimaryKeys(entities, rs)).length;
```

改为:
```java
      query.executeBatch(rs -> primaryKey.setPrimaryKeys(entities, rs));
      return entities.size();
```

**Step 2: 可选——在 BatchParameters 中添加注释**

`applyBatchParameters()` 方法中中间 `executeBatch()` 调用仅用于控制 JDBC 驱动端的内存占用，无需关心返回值。添加注释说明即可。

**Step 3: 运行测试确认无回归**

```bash
mvn test -pl orm
```
Expected: 305/305 通过，0 失败

**风险:** 如果某个 `execute()` 失败，JDBC 会抛出 `BatchUpdateException`，不会静默失败。所以 `entities.size()` 作为返回值是安全的。

## Task 3: 修复 SqlUtil.checkInjection() 正则过严

**Objective:** 允许合法的列名字符（反引号 `` ` ``、`$`），同时不降低防注入能力。

**影响文件:**
- Modify: `orm/src/main/java/.../util/common/SqlUtil.java` (第 10 行)

**Step 1: 修改正则**

将:
```java
  private static final String SQL_PATTERN = "[\\w\\p{IsIdeographic}\\ \\,\\.]+";
```

改为:
```java
  private static final String SQL_PATTERN = "[\\w\\p{IsIdeographic}\\ \\,\\.\\$`]+";
```

**说明:** 新增 `\\$` 和 `` ` `` 字符：
- `$` — 某些数据库中列名可能包含 `$`（如 Oracle 的 `:NEW`、`:OLD` 引用）
- `` ` `` — MySQL 的反引号标识符引用（如 `` `column` ``）
- 原有 `\\w` 已涵盖 `[a-zA-Z0-9_]`
- 原有 `\\p{IsIdeographic}` 涵盖 CJK 汉字
- 原有点号 `.` 支持 `table.column` 引用

**安全说明:** 反引号和 `$` 不能用于 SQL 注入攻击构造（注入需要 `'`、`;`、`--`、`/*` 等字符，这些仍然被拒）。此正则仅用于 ORDER BY 和列名字段的白名单校验，不会出现在值绑定位置上。


## 风险和备选方案

| 问题 | 风险 | 备选 |
|------|------|------|
| #13 ThreadLocal 泄漏 | Web 容器线程复用环境下，若未调用 `remove()` 可能残留 Date 引用。但 `SqlLog` 仅在日志输出时短暂使用，无后续操作，GC 周期内即可回收，风险极低 | 使用 `DateTimeFormatter` + 新 `java.time` API 重构整个格式化逻辑，但改动面较大 |
| #14 `entities.size()` | 若数据库实际插入行数少于实体数（trigger、约束等），返回计数偏高。但 JDBC `executeBatch()` 已抛异常或返回 0，不影响计数语义 | 方案 B：修改 `Query.executeBatch()` 收集中间 `executeBatch()` 结果并聚合，改动面更大 |
